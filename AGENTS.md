# Project GU — Engineering instructions

- The project owner approves gameplay vision, scope, and acceptance. Codex leads technical architecture, API investigation, implementation, integration, debugging, and automated verification. ChatGPT supports systems design, lore, progression, balance, requirements, and design evaluation. For the Gu Framework V2 reconstruction phase, Claude acts as lead framework engineer under the owner's approval gates. Outside that assignment Claude is an optional independent reviewer for high-risk decisions.
- **Development philosophy.** The ultimate project vision takes precedence over preserving any particular implementation. Existing systems may be removed, rewritten, replaced or redesigned when that produces better gameplay, deeper simulation, a better player experience, stronger extensibility or a more convincing living world. Preserve the worthwhile ideas and intended experiences. Do not assume the current implementation is their best expression. Past effort informs decisions but creates no obligation to keep inadequate architecture.
- **Ask first.** Before a drastic change, a substantial redesign, a major feature removal or a consequential gameplay change, present the reasoning, alternatives, expected benefits, migration implications and costs to the owner and wait for approval. Routine bug fixes, diagnostics, refactoring inside approved boundaries and verified preparatory work do not need separate approval.
- Start with the relevant source, Defs, saves and documentation. Use [architecture](ARCHITECTURE.md), [vision](docs/PROJECT-VISION.md), and [roadmap](docs/ROADMAP.md) for orientation. Scale investigation to the change. For uncertain engine behavior, inspect the actual target assemblies or matching decompiled code and run focused probes. Use RFCs for substantial architectural decisions, and resolve scope or gameplay tradeoffs with the owner.
- Target RimWorld 1.7 Waylith and .NET 10. Verify API signatures and lifecycle assumptions against that version. Keep proprietary assemblies, decompiled game source, compiled artifacts, private saves, logs, credentials, and unlicensed assets out of Git.
- Keep package IDs, Def names, Scribe keys, migration semantics and population conservation intact unless the owner approves a change with a migration path. Validated behavior is a regression baseline, not a permanent constraint. Keep species definitions, individual identity, and aggregate cohorts separate. Give each individual exactly one authoritative placement. Prefer optional species behaviors and bounded simulation.
- For C# or XML changes, run relevant structural checks and `scripts/verify.ps1` with actual 1.7 assemblies when available. Record the environment and blockers. Label static checks, stub-based tests, real compilation, player reports, and independently reproduced game tests separately. Exercise save/load and regression cases appropriate to the change. Never modify original historical saves.
- Keep commits focused and state what changed and what was verified. Update affected status docs when evidence changes. Work on the designated development branch. Merge into main only with explicit owner authorization.
